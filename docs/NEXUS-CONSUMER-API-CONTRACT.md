## 2. Ownership and canonical tenancy

IS is one deployable modular monolith. Identity owns authentication, stable global identities and subject resolution, OAuth/OIDC credentials/issuance/revocation, trusted issuer/key policy and global security eligibility. Nexus owns canonical UUID tenants, lifecycle, central memberships, tenant application entitlements, approved domains, consumer tenant grants and effective tenant-access decisions. Its public service interface must not expose storage/Next.js details. Future extraction must preserve issuer/audience/resource identities or explicitly migrate them.

Consumers own their data, application sessions, resource-level roles/permissions, resource-to-tenant mappings and transaction boundaries. Billing owns commercial state and must use reviewed service/events to request entitlement policy changes; it must not write Nexus/Identity tables. Stage 2 does not integrate Billing.

One canonical tenant UUID is propagated unchanged through Sandcastle → IG → Axtor. Workspaces, projects, creative profiles, job queues and operational subdivisions are local resource concepts unless a separately reviewed business requirement establishes a distinct tenant. Participation by another application never creates a tenant. Existing IG UUIDs are preserved where valid and collision-free; the separate compatibility matrix governs collisions and migration proof. Tenant keys/names, email domains and hostnames are not identity or authorization proofs.

## 3. Principal and credential model

| Term | Authoritative source | Never sufficient |
| --- | --- | --- |
| Caller | Validated access token/client authentication and active Identity client → Nexus application/environment binding | `X-Client-ID`, body `caller`, network origin alone |
| Actor | Identity-verified human subject or Identity-registered service/agent principal, with a live scoped delegation/grant | Body/header user ID, email match, Axtor instance ID, arbitrary signed third-party token |
| Tenant | Canonical Nexus UUID selected and authorized against current membership/grants | Header tenant ID, Host, forwarded host or requested UUID alone |
| Target | Registered application/resource audience and allowlisted operation, optionally an opaque local resource reference | Arbitrary URL, app key string or claimed owner/admin resource role |

An OAuth `client_id` claim in a human token identifies the client to which authorization was granted; DPoP proves presentation by the associated key. Nexus additionally resolves the active, environment-specific application binding. Credential class (human, service or registered agent) must come from Identity-validated grant/issuance metadata, never from a caller flag, a user-table existence probe or the spelling/equality of `sub` and `client_id`. A client-credentials subject collision must never become human access. An access token's `sub` must pass Identity's subject resolver to the stable IS user ID; do not assume public/pairwise OIDC `sub` always equals `user.id`. Unsupported subject formats fail closed. APIs expose verified `(issuer, subject)` references, not arbitrary user-directory queries.

**Human mode:** server-side BFF obtains an OAuth access token using Authorization Code + PKCE S256 with an explicit Nexus resource and least-privilege scopes. OIDC ID token establishes consumer login only. The BFF retains user tokens and its own secure application session; tokens are not placed in browser storage. Consumer UI → BFF mutation requires the consumer's own session/CSRF protection. Nexus consumer APIs do not accept IS cookies as an alternate authentication mechanism. Existing IS management cookie routes remain separate.

**Service mode:** a confidential, explicitly registered service obtains its own client-credentials access token, using `private_key_jwt` with registered keys, exact token-endpoint audience, <=60-second assertion lifetime and replay-checked `jti`. Existing first-party login clients are not automatically upgraded. Service/agent principals are distinct from human users and require explicit active Nexus grants for tenant/application/operation. A machine token confers no human membership or impersonation authority. IG/Sandcastle/Axtor environments have different clients and keys; no preview→production grants.

Token-endpoint DPoP proofs bind method/URL/key and nonce but have no resource access-token hash; protected-resource proofs also require the token hash.

**Presentation:** v1 requires sender-constrained DPoP access tokens and RFC 9449 proofs using a vetted implementation. Authorization scheme is `DPoP`; proofs bind HTTP method, normalized exact URL, token hash, key and short proof time, with shared replay protection across instances and server nonce handling. No cookie, API-key, ID-token, unsigned JWT or ordinary Bearer fallback. The implementation spike must prove compatible issuer and verifier support; if unavailable, delegation stays disabled until a reviewed dependency/provider decision. Do not implement custom signing, encryption, DPoP or JWT validation.

**Audiences:** provision one exact HTTPS resource URI per environment for Nexus and each receiving API. Examples `https://is.example/api/nexus/v1`, `https://ig.example/api`, `https://axtor.example/api` are placeholders, not deployed configuration. A token has exactly one allowed audience. Pin the exact discovery issuer (including any path), algorithm allowlist, trusted JWKS location and `typ=at+jwt`/`application/at+jwt`. Require `iss`, `sub`, `aud`, `exp`, `iat`, `jti`, `client_id`, scopes and `cnf.jkt`; validate `nbf` when present. Reject any missing/mismatched audience and ID-token type even if signature is valid. Do not fetch issuer/JWKS from untrusted token URLs. Validate provider active/revoked state and current client/app/grant eligibility on every authorization call; signature alone is insufficient. Clock tolerance is at most 5 seconds and may not extend delegation/grant absolute expiry.

Standards basis: resource indicators ([RFC 8707](https://www.rfc-editor.org/rfc/rfc8707.html)), JWT access-token profile ([RFC 9068](https://www.rfc-editor.org/rfc/rfc9068.html)), DPoP ([RFC 9449](https://www.rfc-editor.org/rfc/rfc9449.html)), client assertions ([RFC 7523](https://www.rfc-editor.org/rfc/rfc7523.html)) and OAuth security BCP ([RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html)). These are standards choices for the proposal, not claims about live configuration.

## 4. Scopes and application boundaries

| Scope | Credential class | Ceiling |
| --- | --- | --- |
| `nexus:tenants:read` | Human or service | Authorized tenant identity; human discovery restricted to that caller application |
| `nexus:membership:self` | Human | Own membership only; no `userId` parameter |
| `nexus:access:evaluate` | Human | Own access to the calling app only |
| `nexus:entitlements:read` | Human or service | Own registered app and authorized tenant only |
| `nexus:service:evaluate` | Service/agent | Own app; live actor evidence or explicit workload grant required |
| `nexus:delegation:create` | Human | Root grants for self and allowlisted workflow only |
| `nexus:delegation:revoke` | Human or service | Root owner or participating service, per family visibility rules |
| Target operation, e.g. `ig:jobs.submit`, `axtor:jobs.execute` | Exchanged human-delegation token | Single receiving audience and server-registered operation ceiling; never Nexus/IS admin authority |

Requested scopes are intersected with client resource grants, credential class, principal policy and active tenant grants; OAuth registration alone grants none of them. Nexus cannot issue target operation names that the receiving application's registered policy does not support. Application owners approve operation semantics; these example names do not claim those routes already exist. No wildcard scopes/tenants/audiences and no consumer scope authorizes `/api/admin/*`, `/api/nexus/registry/*`, `/api/nexus/operators` or Stage 1 tenant-management writes. Those routes continue requiring their existing session/role/origin checks; do not add token-to-operator adapters.

## 5. Versioned endpoints

Base: `/api/nexus/v1`. All paths are proposals. All requests require DPoP access tokens plus per-endpoint scopes and current authorization. POST bodies are strict schemas (unknown properties rejected), max 16 KiB; token-evidence bodies max 32 KiB. IDs are UUIDs, external subjects opaque strings. Responses include `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `X-Request-ID`; tokens never appear in URLs/logs. No public CORS; v1 is BFF/service-to-service. API POSTs do not use cookie authentication. Rate limits apply per credential/client, tenant and endpoint with bounded request cost.

| Endpoint | Credential / scope | Semantics |
| --- | --- | --- |
| `POST /tenant-resolutions` | Human/service; tenants:read | Exactly one of `tenantId` or ASCII approved `domain`; return only an authorized canonical tenant |
| `GET /me/tenants?limit=…&cursor=…` | Human; tenants:read | Only initialized, active tenants with active self-membership and an enabled entitlement to the calling app; no arbitrary subject or application filter |
| `GET /tenants/{tenantId}/membership` | Human; membership:self | Own active role/status/version only; no member directory |
| `POST /access-decisions` | Human; access:evaluate | `tenantId, applicationId, operation, resource?`; `applicationId` must equal caller binding; actor derives only from the access token |
| `GET /tenants/{tenantId}/applications/{applicationId}/entitlements` | Human/service; entitlements:read | Calling app only; active visible tenant context; return current boolean effective entitlement and revisions, no billing data |
| `POST /service/access-decisions` | Service/agent; service:evaluate | `tenantId, applicationId, operation, resource?, actorEvidence?`; human evidence required for on-behalf-of access; absence means explicit workload grant, never inferred human |
| `POST /delegations` | Human; delegation:create | Create a short root grant bound to caller, self, tenant, exact ordered app/operation path and optional resource ceiling; no caller-supplied subject |
| `POST /delegations/{grantId}/revoke` | Human/service; delegation:revoke | Revoke visible root and all descendants; reason required; idempotent for authorized family, no unauthorized existence disclosure |

Pagination uses an opaque signed/encrypted cursor produced by a vetted library or server-side cursor storage, bound to caller, subject, tenant/application filter and query version, expiring after 5 minutes. Limit default 50, maximum 100. Reauthorize each page against live state; a cursor is not an access grant. No total count and no ordering/timing/error hints about hidden tenants. Stable UUID ordering, bounded scans and rate limits are required. Changed eligibility may remove rows between pages; no stale eligibility snapshot across requests.

Domain resolution accepts a strict lowercased ASCII A-label hostname (1–253 chars), no port, trailing dot, IP literal, scheme, path, wildcard or forwarded-header substitution. Non-ASCII must be canonicalized by an approved IDNA library before calling; the server still validates the A-label. **Existing `nexus_tenant_domains` rows are associations only.** Resolution requires a separate current operator-approved domain record bound to the same tenant and association revision, with verified ownership or an audited platform-managed-domain decision. Legacy/unapproved/revoked/expired/ambiguous mappings return the same unavailable result. No DNS/HTTP fetch from a resolution request; verification is a separately authorized administrative workflow.

## 6. Evaluation, visibility and errors

Human effective access requires: both membership and consumer gates enabled; valid, current Identity token/principal; active caller client/application binding; active canonical tenant with initialized governance; active membership; active target application; enabled tenant–application entitlement; endpoint scope; operation allowlist; and, for delegation, active family/ancestor grants, permitted path, current policy revisions and recipient binding. Member/owner/admin do not map to local resource roles. Provider/grant/global security failures deny; a future global block must precede any tenant admission. Do not invent a global block feature that does not exist today.

Workload-only access substitutes a specific current service/agent tenant grant for human membership. It still requires active initialized tenant, active caller/target app and enabled entitlement, scope and operation ceiling. There is no global service superuser. Human mode and workload mode are discriminated explicitly; service evidence containing a human subject cannot be silently downgraded to workload when invalid. Consumers must not use workload grants to bypass a failed human check.

Actor evidence is an Identity-issued access token presented **as evidence**, not as the request's authorization credential. A service request is authorized by its own Nexus-audience DPoP token. Evidence must target that receiving service's registered API audience and must match a live delegation edge/family, tenant, operation/resource and actor. Nexus verifies it through the internal Identity token-validation interface. It never treats evidence as a generic Nexus-audience bearer token and never accepts a claimed `actorId`. This narrowly scoped validation is unavailable on ordinary human endpoints. Evidence-key possession is required at the actual receiving application's DPoP-protected HTTP request; Nexus uses receiver authentication plus live edge binding when verifying already-received evidence. The service must carry out that HTTP proof validation before acting or forwarding.

All eligibility reads use one bounded, consistent database snapshot (including version/grant/client state through the Identity interface). Decisions are never assembled from independently stale caches. A snapshot acquired after revocation commits must deny. A decision racing a change may reflect the earlier snapshot, subject to the strict validity budget below. No resource operation is performed in the Nexus decision transaction; the consumer performs its own tenant/resource check and authorization.

Error order prevents enumeration: validate credential/proof/class/scope before target lookup. Malformed request 400; invalid credential/proof 401 with the standard challenge; valid credential lacking endpoint scope/class 403 before resource lookup. Identity authorization, tenant or policy-store outage is 503, never a stale allow or permissive empty result. For authenticated, in-scope decisions, return 200 `allowed:false, code:access_denied` without tenant/member/entitlement/version details when the requested context is unknown, uninitialized, suspended, unentitled, inactive, cross-tenant or outside the caller grant. The same denial shape applies to all; only internal audit captures reasons. Missing/hidden identity/membership/entitlement/domain lookup returns uniform 404 `resource_not_available`. No 409/403 reason leaks the presence of another tenant. Visibility of a root grant requires actor ownership or a recorded, active participant; inaccessible grants return the same 404 as absent grants. Operational failures have sanitized request IDs, never SQL/token details. Rate limit is 429 plus Retry-After; no token-derived details in descriptions.

Successful identity/membership/entitlement lookups require effective visibility to the calling app and return only that tenant/self/current app's data. An unentitled caller does not learn whether an entitlement exists; use the generic negative access decision. This deliberately makes an entitlement GET unavailable rather than exposing disabled configuration. A visible entitlement is `{enabled:true,effective:true}` in v1; future quantitative grants require an explicitly versioned schema. Tenant discovery returns only effective entries, not a catalogue of inactive or suspended memberships.

## 7. Delegation profile: Sandcastle → IG → Axtor

Use [RFC 8693 token exchange](https://www.rfc-editor.org/rfc/rfc8693.html) at Identity's discovered token endpoint, not a custom signing endpoint. Root-grant creation/revocation is a Nexus policy operation; Identity authenticates clients/subjects and issues/validates OAuth tokens using the existing provider and vetted protocol support. The installed provider's raw `issueTokens` interface does not enforce authorization ceilings itself; a compatible vetted exchange component or reviewed policy extension must enforce this entire profile before calling it. Do not advertise token exchange until interoperability/security tests pass; no fallback to header impersonation if provider work is blocked.

1. Sandcastle BFF obtains a human Nexus access token `T0` (audience Nexus, verified subject, client_id=Sandcastle, DPoP bound to Sandcastle key) through approved user authorization. `nexus:delegation:create` requires explicit client policy and user consent or an audited first-party consent policy; normal login scope alone is insufficient.
2. It creates a Nexus root grant with a canonical tenant and one exact, server-allowlisted ordered path: Sandcastle → IG → Axtor. Each edge lists exact operation names and any opaque resource ceiling. Nexus derives the human actor from `T0`, checks active membership and entitlements for every participating app, binds the source token `jti`, caller client/environment and key, and records a root expiry <=min(T0 expiry, now+120s). The returned `grantId` is a reference, not a credential or a way to select another actor.
3. Sandcastle authenticates at the token endpoint and exchanges `T0` for `T1` targeted only to IG. Form fields: `grant_type=urn:ietf:params:oauth:grant-type:token-exchange`, `subject_token`, `subject_token_type=urn:ietf:params:oauth:token-type:access_token`, `requested_token_type` equal to that access-token type, one `resource` equal to registered IG audience, narrowed `scope`, and the documented extension `nexus_grant_id`. `private_key_jwt` authenticates the caller; a DPoP proof binds the issued token to its sending key. `actor_token`, alternate issuers, ID token subject types, multiple audiences/resources, refresh issuance, arbitrary actor IDs and extra extension fields are rejected in this profile.
4. Identity validates token type/signature/active state and asks Nexus to authorize the exact edge. At the root: caller/client/key/token-jti must match the grant. At a downstream hop: input audience must equal the authenticated receiver's registered resource, token issuance must identify that receiver as the next participant, and the live grant must authorize that receiver's onward edge. A generic valid JWT for IG is not sufficient without the persisted issuance/family link. Prior sender DPoP key is not silently rebound: the parent token is input evidence at exchange, while the new output is bound to the authenticated exchanging caller's key. Each actual IG/Axtor request still validates the sender's original DPoP proof.
5. `T1` retains the verified human `sub`, records current service actor via RFC 8693 `act`, issuing `client_id` Sandcastle, one tenant, one receiving audience, exact operations/resource ceiling, parent/root IDs and policy versions. It is not valid for Axtor, Nexus ordinary endpoints, admin endpoints or another tenant. Sandcastle sends `T1` with its DPoP proof to IG.
6. IG validates incoming token/proof/family, maps its local resource to the **same canonical tenant**, and uses its own client-credentials Nexus token plus `T1` as actor evidence to obtain a current IG tenant-access decision. It also enforces local IG roles/resource authorization. If further execution is authorized, IG exchanges `T1` under IG's own client authentication for `T2`, audience Axtor, key-bound to IG, with a strictly permitted narrower edge. It never forwards `T1` to Axtor as Axtor authorization.
7. Axtor validates `T2` and IG's proof, obtains its own Nexus decision using its own credential plus `T2` evidence, checks local action/resource permissions and canonical tenant, and executes only within the decision deadline. Axtor's internal agent instance IDs do not become global actors. An independent agent requires an explicitly registered Identity agent principal and Nexus workload/delegation grant; that may not impersonate a human.

Delegated access JWTs use the strict profile-private claim `urn:nexus:authorization:v1` with `tenant_id`, `root_grant_id`, `parent_jti`, `receiver_application_id`, `operations`, `membership_version`, `policy_versions`, `depth` and optional `resource_ceiling`. The namespace is a claim name, not an audience or network endpoint. `sub` remains the verified human; `client_id` and current `act` identify the authenticated sending service, while `cnf.jkt` identifies that sender's proof key. For the IG→Axtor child, `act` is IG with Sandcastle in nested history; it never overwrites the human actor. Scope/operation comparisons use the registered target policy. Provider-owned fields are never overridden by custom claims. Root human tokens and pure client-credentials tokens do not gain tenant rights by adding an unverified context object; only persisted, live exchange issuance can establish this context. The OpenAPI includes its strict context schema; consumers verify signed claims through vetted token verification and still obtain the online decision.

Maximum two delegation edges; no cycles, audience fan-out, escalation or arbitrary audience translation. Each child retains the same human actor and tenant, is limited to its next edge, expires <=min(parent expiry, root expiry, now+60s), and receives no refresh token. Scope comparison is against the server's edge operation map, not a naive string subset between IG and Axtor namespaces. The root authorizes each exact edge; downstream tokens cannot append edges or resources. Nested `act` entries record history, not additional independent privileges. The current service actor and human subject remain distinct.

Persist each issuance `jti`/provider token reference, parent, root, caller/recipient, tenant, actor and policy versions. A root revocation invalidates all descendants immediately at online checks; RFC 8693 by itself does not provide this cascade. Exchange/revoke transactions serialize on the root so a revoke committed before exchange completion cannot create a usable child. In-flight actions remain bounded by the decision validity budget, not by the token TTL. Token exchange and revocation are audited atomically with policy state; sensitive issuance fails if audit persistence fails.

## 8. Revisions, freshness and revocation

Stage 1 membership version is an optimistic integer maintained by the service. Stage 2 must ensure every role/status write, including authorized maintenance SQL, advances it; deletion/recreation must not reset an authorization epoch. A persistent membership-version tombstone keyed by `(tenant_id, stable IS user ID)` must seed reinsertion with a higher version, rather than returning to Stage 1’s default 1. Add monotonic sidecar epochs for tenant/governance/domain eligibility, app registration, entitlement pair and consumer grant, with tombstones for deleted/recreated keys. Provider client/token/session eligibility is supplied by Identity. Timestamp equality and process-local counters are not authorization versions. Do not edit 0007 or weaken its last-admin triggers.

A positive decision includes opaque `decisionId`, verified actor/caller, tenant, target/operation, `evaluatedAt`, `validUntil`, membership version (human only) and policy epochs. The token/family binds the versions at issuance. Any relevant epoch change invalidates that family permanently; reactivation does not resurrect a previously revoked/invalidated grant. API reads evaluate live versions. Versions are advisory evidence to consumers, not credentials or proof of current access; consumers cannot submit an old version to force a stale allow. Denials expose no hidden versions.

| Item | v1 maximum / rule |
| --- | --- |
| Human Nexus access token | 300s, no offline_access in v1 consumer profile; live token/principal checks still mandatory |
| Client-credentials token | 60s, no refresh |
| Root delegation | 120s and never beyond original subject-token expiry |
| Delegated child | 60s, never beyond parent/root expiry; no renewal without fresh authorization |
| Decision evaluation | <=2s bounded DB/Identity transaction; expiry anchored to snapshot-acquisition time, not response time |
| Positive authorization cache | 0s in Nexus and clients; every protected operation requires online decision |
| Decision consumption | <=5s from snapshot `evaluatedAt`, also bounded by token/grant expiry; consumers reject delayed responses |
| Max stale authorization after committed change | **5s for a decision already in flight**; calls whose snapshot starts after the change deny immediately |
| Advisory UI tenant metadata cache | <=15s, never used to authorize; all API responses still no-store |
| Token/grant/client introspection cache | 0s for allow decisions, exchanges and execution; fail closed on outage |
| JWKS | <=300s, single bounded refresh on unknown kid; trusted key retirement/compromise policy may invalidate immediately |

Sensitive operation queues must recheck at dispatch/execution and each separately authorized side-effect boundary; an enqueue-time decision is not a perpetual execution lease. Work requiring authorization beyond 5s needs a new online decision; no implicit long-running agent lease. Nexus cannot atomically undo already committed consumer operations. Consumers own compensation/idempotency and must not promise instantaneous termination of running work or existing application sessions.

Membership deactivation/demotion, tenant suspension, entitlement disable, app/client disable, caller-grant revocation, Identity principal/token revocation, domain approval revoke and root revoke are checked on each relevant call. No dependence on an eventually delivered event for security. Optional invalidation events/outbox may improve UI/observability later, but are not a v1 authorization prerequisite or a replacement for online checks. Stage 1 global permit removal is login admission, not session revocation; distinguish it from actual Identity suspension/revocation until the latter exists.

## 9. Audit, publication and review gates

Existing membership/registry mutations remain transactionally audited. New consumer grants, domain approvals, operation policies, delegation issuance/revocation and credential-binding changes require durable actor/caller/tenant/target/reason/request/time/version events. Decision audit records store decision ID, normalized outcome and internal reason category, operation and revisions; no full tokens, secrets, client assertions, DPoP proofs, raw bodies or unnecessary personal data. External consumers see only uniform denial; internal audit access is an independent privileged concern. Security-relevant decision audit must be durable before positive response; use an audit write/outbox in the bounded evaluation transaction, fail closed on audit failure and prevent unbounded negative-request log amplification with redacted aggregation/rate limits.

The contract/OpenAPI are draft `1.0.0-draft.1`. No route or scope is released by publishing these files. Contract review must approve: DPoP/private-key client provisioning; the 5s in-flight budget and no positive cache; root/child lifetimes; consumer tenant grants and operation graph; verified/platform-approved-domain workflow; subject resolver; and the provider interoperability choice. Deployment/activation verification, target ledger/grants, security tests and consumer rollout are mandatory gates in the implementation plan. Runtime work starts only after contract review; production/consumer changes require separate authorization.


Stage 2C.1 review: [credential lifecycle and provider integration](STAGE-2C1-CREDENTIAL-LIFECYCLE.md) records isolated opaque/JWT evidence, recommends JWT with a positive issuance/revocation registry, specifies maintained resource-server nonce composition and durable subject mappings, and revises Stage 2D entry gates. These are recommendations awaiting review; existing authorization rules remain in force and consumer routes remain unauthorized.

Registry/revocation generations, maintained resource-server nonce composition, subject mappings and candidate 0008 are implemented and validated only in disposable infrastructure. No consumer route or production/persistent activation is authorized; outstanding administration, grant-lifecycle and security integration gates remain explicit.
