### Proposed schema responsibilities, not SQL

- Nexus-owned state: monotonic epoch/tombstone records; approved domains; application/environment/caller tenant-operation grants; edge policies; root/issuance lineage/revocation records; audit/outbox. Restrictive FKs and retention reviewed to avoid deleting existing identities/tenants or historical evidence. Grant IDs and token IDs are references, never access credentials. Do not store raw tokens/assertions/proofs; opaque provider references or one-way lookup digests only.
- Existing membership `version` is advanced by Stage 1 service code. A persistent per-tenant/user membership-version tombstone must survive deletion and seed a higher reinsertion version. New trigger/ownership logic must guarantee raw maintenance/bulk writes cannot silently keep/reset it, while leaving the last-admin counter functions unchanged. Entitlement `updated_at` alone is not a revision; add sidecar pair epochs that survive delete/recreate. Update lifecycle/domain/entitlement/client-policy changes and audit/epoch in the same commit, including existing mutation paths.
- Identity-owned state: OAuth resource/client grants/keys, protocol replay/nonces and token lifecycle via supported provider APIs/schema. Per-client resource enforcement and disabled registration remain explicit. Provider initialization that seeds resources must be removed from unapproved production startup paths or gated behind authorized provisioning; never mutate OAuth registrations as a hidden side effect of release.
- Root/child policy and provider token issuance cross module boundaries: propose an internal orchestrator and atomic provider/Nexus persistence when supported. If issuance occurs outside the Nexus DB transaction, persist a pending reservation then activate only after both stores and audit agree; validators reject pending/orphan state and failure cleanup revokes the provider token. Crash before/after each phase must not create a usable grant. Root revoke wins through family state checked online even for unexpired provider JWTs.

## Deployment and versioning strategy

1. Verify immutable deployed Stage 1 SHA, flag value for the actual production/preview deployment, exact target DB branch and ledger, and tenant governance before reliance. Project-level current config is insufficient to prove an older deployment's runtime configuration. Record evidence without secret values. If flag is off/unknown or dependency readiness fails, consumer routes remain unavailable. A proposed `NEXUS_CONSUMER_API_ENABLED` gate defaults off and also requires the membership foundation to be explicitly active; it never makes management APIs public.
2. Obtain separate authorization for isolated schema/protocol provisioning rehearsal. Audit current provider schema, migration numbers/checksums, runtime role permissions, verified-TLS direct connection, backup/restore capability and lock budget. Rehearse fresh and populated 0007 branches, policy-version updates, immutable last-admin behavior and previous deployed code compatibility. Do not use previews pointed at production for security testing.
3. Deploy reviewed IS changes only with explicit authorization, gate off. Provision approved resources/scopes/keys/client grants via supported privileged Identity APIs in an authorized environment; keep original login clients/issuer/callbacks intact. Do not enable public registration or automatically grant every client every resource. Verify no mutation in passive startup/readiness.
4. With subsequent authorization, enable scoped synthetic/test tenants and shadow-only consumers. Shadow comparisons never grant access or create resources; differences fail cutover. Domain associations require approval per tenant, and app/entitlement/workload grants are separate from OAuth client validity. Consumer repositories remain untouched until separately authorized.
5. Enable per-environment/per-caller/per-tenant cohorts only after test evidence, consumer deadline/resource checks, operational keys/replay/audit capacity and safe rollback are signed off. Watch redacted denial/revocation latency and replay/rate metrics without logging credential content. Fail closed on missing metadata/Identity/policy/audit dependencies.
6. URL namespace is `/api/nexus/v1`; spec is `1.0.0-draft.1` until approval/implementation. Compatible optional metadata additions may bump minor spec versions; new required fields, error/visibility semantics, auth profiles or stale-access budget changes require new major/profile negotiation and dual validation tests. Consumers ignore documented additive response fields but may not ignore unknown credential/scope/security conditions; request schemas remain strict. Publish supported contract hash/version and deprecation policy only once approved. OAuth discovery remains authoritative for Identity endpoints.
7. Future service extraction preserves canonical UUIDs, Identity subject/issuer semantics, audience/resource identities, revision monotonicity and authorization deadline. Routing may change behind the stable public contract; changing issuer or widening audiences requires its own credential migration. No direct table consumers are introduced.

## Rollback and incident strategy

- Before consumer enforcement: disable the consumer gate and restore prior compatible IS code while preserving additive schemas, memberships, entitlements, approvals, grants, revision tombstones, audit and ledger. Do not change 0007, delete migrations or reset counters/epochs.
- After consumers depend on v1: disabling the API returns unavailable and protected consumer operations must stop. It must not silently reactivate old local policies that ignore central revocations. Freeze affected cohorts and queued side effects; restore a compatible previous v1 implementation or explicit deny mode. Compare local/central memberships and versions before any separately approved legacy recovery.
- For suspected key/client/token compromise: use supported Identity revocation/disable plus Nexus caller/family revocation. Online state checks deny future snapshots; in-flight decisions expire within 5s. Environment feature gates are rollout controls, not a synchronous cross-instance revocation mechanism: persist caller/family/tenant-policy revocation for incident denial rather than relying on an environment redeploy alone. Stop/recheck queued jobs. Provider JWT signatures remaining valid do not authorize access. Audit and review key replacement; secret rotation is not performed automatically by this task.
- Fix bad schema/policy epochs with an additive forward repair under reviewed authorization; preserve tombstones and evidence. A backup restore must reconcile post-backup changes, client/token issuance and grant lineage; never restore a whole database over newer unrelated records as an automatic rollback.
- Migration transaction failure rolls back that revision; earlier runner commits remain. Independently review any provider-schema migration and provisioning rollback. Token issuance/lineage inconsistencies remain unusable and require explicit reconciliation, not an acceptance bypass.
